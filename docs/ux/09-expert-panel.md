# 09. 전문가 패널 검토: 첫 이용자 100명 과정

2026-11-03, 오너 요청: "IT 전문 영업 사원, CEO, 사업 기획자 등을 구성해서 그들의 시점에서 … 평가와 개선점, 말도 안되는 거,
현업에서는 절대 이렇게 하면 안 된다 … 세부적인 프로세스에 대해서 분석해서 보고해."

다섯 관점의 검토자가 서로 모른 채 같은 자료를 읽었습니다. 자료는 [08-first-100.md](08-first-100.md), 조사 문서,
[shape-kickoff.md](shape-kickoff.md), [research/p5-history.md](research/p5-history.md), 그리고 이미 만든 PR 설명(F1~F3, F7a,
F7b, F6, F5)입니다. 경험에서 나온 판단은 [현업 경험상], 원문을 확인한 사실은 [출처]로 구분했습니다.

## 2. 다섯 명이 공통으로 한 말

1. **창업자가 사람을 직접 만나는 일이 운영 루프에 없습니다.** (영업, CEO, 기획, 그로스)
   - 채널 10개가 모두 공개 게시판입니다. 오너 할 일 종류도 게시, 공개, 배포, 결제, 계정뿐입니다.
   - 빠진 것: 지인 명단, 1:1 연락, 데모·같이 설치하기, 후속 연락, 소개 부탁, 고객 명단.
   - 우리 조사 문서도 같은 결론을 냈습니다. "첫 사용자는 창업자가 직접 한 명씩 모집한다"(PG), "B2B 첫 10곳은 지인 > 정밀 콜드 > 투자자 네트워크". 그런데 이 결론이 08 설계에 들어가지 않았습니다.
2. **판정 숫자가 관심 단계(star)에 머물러 있습니다.** (그로스, CEO, 기획)
   - 3단계(관심 → 첫 가치 → 반복)를 만들어 놓고도 판정은 star로 합니다.
   - 8절 완료 기준("다음 실험을 스스로 제안한다")은 기계가 도는지를 재는 기준입니다. 사용자가 0명이어도 참이 됩니다.
3. **지시서가 길면서 정작 필요한 칸이 빠졌습니다.** (기획, CEO, 영업, 사용자)
   - 빠진 칸: 이미 가진 것(지인, 아는 손님), 오너의 주당 시간, 대안 대비 가치, 리스크(사전 부검).
   - 조사 문서(kickoff-interview B3)에는 있었는데 08로 옮기면서 사라졌습니다.
   - 남은 칸 중 일부는 과합니다. 조직, 보고 방식, 기본 결정 권한은 설정의 기본값이면 됩니다.
   - 20턴 안에 15칸을 다 채울 수 없습니다. 확인 턴을 빼면 실제 질문은 12~14개입니다.
   - "모르겠어요"를 두 번 하면 필수 칸이 "정리됨"이 되어, 목표나 대상이 비어도 승인됩니다.
4. **사용자가 열 명 단위일 때 통계식 회고는 잡음입니다.** (영업, CEO, 기획, 그로스)
   - 그 시기에는 사람별 이야기로 판단해야 합니다. 누가, 어디서 와서, 어디서 막혔고, 무슨 말을 했는지입니다.
   - "반응 없는 채널은 뺀다"를 게시 한 번 결과로 하면 운을 학습하게 됩니다.
5. **오너 시간을 하나로 묶어 줄이려 합니다.** (CEO, 영업, 사용자)
   - 고객과 보내는 시간은 늘려야 하고, 기계 출력을 검토하는 시간은 줄여야 합니다. 둘을 따로 재야 합니다.
6. **이 제품 자신을 Show HN에 내기에는 장벽이 큽니다.** (그로스, 영업, CEO)
   - Docker, 워커, Claude 유료 구독이 있어야 써 볼 수 있습니다.
   - Show HN 규칙: "Please make it easy for users to try your thing out, ideally without barriers such as signups or emails" [출처: news.ycombinator.com/showhn.html].
   - 출시 기회는 사실상 한 번입니다. 준비가 확인되기 전에는 쓰면 안 됩니다.

## 4. 바로잡을 사실과 버그

- **오너가 직접 한 말이 "짐작"으로 붙습니다.** 사용자 검토자가 05번 화면에서 찾았습니다. "개인정보 든 로그는 절대 밖으로 나가면 안 돼요"가 금지선 칸에 "짐작"으로 붙었습니다.
  - 원인은 F7a 수정 규칙입니다. "직전에 물어본 칸에만 '오너가 말함'"이라서, 오너가 다른 칸 이야기를 먼저 하면 짐작으로 낮아집니다.
  - 고칠 방향: 모델이 오너 답의 **원문 일부를 그대로 인용**하게 합니다. 서버가 그 인용이 실제로 오너 답에 있는지 확인되면 칸과 상관없이 "오너가 말함"으로 둡니다.
- **5절의 "GitHub이 부탁을 금지한다"는 과장입니다.** GitHub 원문은 자동 star와 가짜 활동만 금지합니다.
- **GeekNews 규칙은 공개돼 있습니다** [출처: news.hada.io/guidelines]. 자기 프로젝트는 Show로만, 같은 프로젝트는 일정 기간 재등록 불가, 추천 요청 금지, 대량 생산 콘텐츠 제한입니다. 채널 목록에서 "확인 못 함"을 "확인함"으로 고칩니다.
- **5절의 "채널마다 다시 올리기 규칙"이 `channels.yaml`에 아직 없습니다.**
- **08 4절 마크다운이 깨져 있습니다.** 회고 표가 루프 그림 사이에 끼어 있습니다.
- **README와 PRODUCT.md에 Codex 요구가 남아 있습니다.**

## 5. 실사용자가 그만두는 순간

- **설치.** 1~2시간이 걸립니다(추측). 터미널 두 개, 샌드박스 빌드, 로그인 주소 복사. PC가 꺼지면 회사가 멈추는지 설명이 없습니다.
- **연결.** 1시간 넘게 걸립니다(추측). 지금 왜 필요한지 모르는 연결을 한꺼번에 요구합니다. Gmail "확인되지 않은 앱" 경고도 넘어야 합니다.
- **승인 뒤의 침묵.** 오너 할 일, 결정 카드, 브리핑 화면이 아직 없습니다. 사이드바 메뉴는 12개입니다.
- **말.** 화면에 `door_policy`, deny, 플레이북, 할당량 같은 내부 용어가 그대로 보입니다. 사업, 프로젝트, 주기, 도전, 업무라는 그릇 다섯 개가 헷갈립니다. "짐작"이 출처와 확신도 두 곳에서 다른 뜻으로 쓰입니다.
- **비용.** Max 구독자에게 "USD 환산" 상한은 감이 오지 않습니다. "이번 주 구독의 몇 %"로 보여야 합니다.
- **시간(추측).** 처음 3~4시간, 하루 20분, 주 3~4시간입니다. 지금 상태에서는 하루 40분이 넘고, 그러면 2주 안에 그만둡니다.
