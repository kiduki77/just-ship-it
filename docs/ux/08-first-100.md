# 08. 아이디어에서 첫 이용자 100명까지

2026-11-03 오너 지시를 설계로 옮긴 문서입니다. [07-roadmap.md](07-roadmap.md)의 사업·도전 구조와
[BACKLOG.md](../BACKLOG.md)를 바탕으로 하고, 둘과 다른 곳은 이 문서가 우선합니다.

## 0. 목표

> 오너가 아이디어와 어느 정도의 사업 기획을 주면, 회사가 결정, 로드맵, 구현, 홍보, 세일즈, 성과 분석,
> 고객·메일 관리까지 사장과 함께 사업 초기를 대신한다. 목표는 첫 이용자 100명이다.

100명은 보장이 아니라 목표입니다. 이 소프트웨어가 하는 일은 "어떻게 할지 모르겠고 귀찮고 어렵다"를 없애서 도전을
쉽게 만드는 것입니다. 그래서 회사가 나아지는지는 두 숫자로 봅니다.

- **북극성 숫자.** 출발 경로마다 다릅니다(1절).
- **도전 속도.** 첫 이용자까지 걸린 날 수, 주당 끝낸 도전 수, 오너가 쓴 시간.

## 2. 출발 경로가 회사를 정합니다

지금은 조직(`config/agents.yaml`)도, 측정(수동 KPI)도, 회사의 할 일(보고서)도 하나로 고정돼 있습니다.
바꿀 모습은 **출발 경로 정의(플레이북)** 하나가 아래를 정하는 구조입니다.

| 플레이북이 정하는 것 | 예: 오픈소스 | 예: 모바일 앱 |
|---|---|---|
| 북극성 숫자와 세는 법 | GitHub star 100 | 다운로드 수 (앱스토어·플레이 합산) |
| 앞선 신호 | issue·PR, README 방문, 클론 | 스토어 노출 대비 설치율, 첫날 유지 |
| 수집기 | GitHub API | App Store Connect, Play Console |
| 추가 역할 | 개발자 관계(문서·예제·issue 응대) | 앱 관리(스토어 등록, 심사, 리뷰 응대, ASO) |
| 주요 채널 | Show HN, 서브레딧, 개발자 뉴스레터(TLDR, Console.dev), Awesome List | 지인 베타(TestFlight), 스토어 검색(ASO), Product Hunt |
| 오너만 할 수 있는 일 | 커뮤니티 게시와 댓글 응답, 저장소 공개, 라이선스 결정 | 개발자 계정 등록·결제, 심사 제출 |
| 한 주기의 모양 | 준비(README, 1분 설치) → 지인 피드백 → 출시 주 → 이슈 응대와 주간 릴리스 | 베타 → 스토어 등록·심사 → 출시 → 리뷰 응대와 ASO |

경로 6개(오픈소스, 모바일 앱, 웹 서비스, B2B, 뉴스레터·커뮤니티, 확장 프로그램)의 전체 표는 부록 A에 있습니다.

**허영 숫자에는 실사용 숫자를 붙입니다.** star와 다운로드는 오너가 고른 북극성 숫자 그대로 씁니다. 다만 가짜 star가 흔하고
(약 310만 개로 추정한 연구가 있습니다), 다운로드만으로는 실제로 쓰는지 모릅니다. 그래서 북극성 카드 옆에 실사용 숫자를 항상
같이 보여 줍니다. 오픈소스는 외부 issue·PR과 고유 방문자, 앱은 7일 안에 핵심 행동을 한 설치입니다. 카드에는 세는 법을
늘 적어 둡니다.

**조직 조립.** 회사는 공통 핵심 역할에 경로 역할을 더해서 만듭니다.

- 공통 핵심: CEO, Research, CPO + 개발팀, Growth, Analyst, Risk(검토)
- 경로 역할: 경로가 고릅니다
- 지시서 역할: 시작 대화에서 오너가 요청하거나 CEO가 제안하고 오너가 승인한 역할

역할 정의는 지금처럼 프롬프트와 도구 목록입니다. 사업마다 켜진 역할 목록과 그 이유가 업무 지시서에 남습니다.
경로를 바꾸면(예: 오픈소스에서 호스팅 유료판으로) 지시서의 새 판으로 조직도 바뀝니다.

## 3. 시작 대화와 업무 지시서

### 3.1 왜

회사가 오너와 다르게 이해한 채 일하면 오너는 "이상하게 한다"고 느끼고, 나중에 "왜 이렇게 했어, 다시 해"가 됩니다.
P-5에서는 CEO가 오너 답을 받기 전에 계획을 짰고, 27분 뒤 방향이 바뀌어 업무 24%가 버려졌습니다.
시작 대화는 한 회사가 다른 회사에 일을 맡길 때 주는 기획서나 업무 지시서를 함께 만드는 대화입니다.

### 3.2 대화 규칙

1. **한 번에 하나만 묻습니다.** 한 턴은 질문 하나이거나 "제가 이해한 건 이거예요. 맞나요?" 확인 하나입니다.
2. **최대 20턴입니다.** 확인 턴도 20에 들어갑니다. 지시서의 필수 칸이 모두 "오너가 말함"이나 "확인함"이 되면
   20턴 전이라도 끝냅니다. 진행 표시는 남은 질문 수가 아니라 지시서가 얼마나 찼는지로 보여 줍니다.
3. **빈칸을 보고 묻습니다.** 질문 순서는 고정하지 않습니다. CEO는 매 턴 지시서 초안의 가장 중요한 빈칸이나 가장 약한 칸을
   골라 묻습니다. 질문 후보는 [kickoff-interview.md](research/kickoff-interview.md)의 G0~G7 묶음입니다.
4. **CEO도 자기 생각을 꺼냅니다.** 눈높이를 맞추려면 오너만 말해서는 안 됩니다. 4~6턴마다 CEO가
   "그래서 저는 이렇게 하려고 합니다. 출발 경로는 X, 첫 2주는 Y, 오너님께 부탁드릴 일은 Z"를 보여 주고 맞는지 묻습니다.
   오너가 고친 곳이 지시서에 바로 반영됩니다.
5. **"모르겠어요"는 정상 답입니다.** 지시서에 "모름"으로 남고, 첫 주기의 조사 도전이 됩니다. 필수 칸이면
   "짐작이라도 괜찮아요"를 한 번 묻고, 그 답은 "짐작"으로 표시합니다.
6. **기존 자료를 먼저 읽습니다.** 오너가 기획서나 메모를 붙이면 CEO가 먼저 읽고 지시서를 미리 채웁니다.
   대화는 빈칸과 확인만 합니다.
7. **끊었다 이어 할 수 있습니다.** "나중에"를 누르면 그 자리에서 멈추고 다음에 이어 합니다.
8. **아이디어를 다듬어 줍니다.** 오너의 처음 아이디어는 대개 거칠고, 본 것 하나에서 출발합니다(오너 결정, 2026-11-03).
   CEO는 받아 적기만 하지 않습니다. 대상을 좁히고, 더 작은 첫 시험을 제안하고, 가장 약한 가정을 짚어서 함께 다듬습니다.
   다듬은 내용은 "확인함"이 되어야 지시서에 들어갑니다.
9. **성공 조건은 대화로 정합니다.** 플레이북의 숫자(star 100 등)는 기본안일 뿐이고, 성공과 중단 조건은 대화에서 오너와 함께
   정합니다(오너 결정). CEO는 관심(예: star) → 첫 가치(실제로 써 봄) → 반복 사용의 세 단계를 보여 주고, 어느 단계의 숫자로
   성공을 판정할지 묻습니다.

### 3.3 업무 지시서의 칸

| 칸 | 내용 | 무엇을 정하나 |
|---|---|---|
| 배경과 목적 | 왜 하는지, 왜 지금인지, 오너에게 무엇이 달라지는지 | 판단이 갈릴 때의 기준 |
| 한 줄 설명 | 누구를 위한 무엇인지 | 모든 업무의 범위 검사 |
| 대상 고객과 문제 | 한 사람의 모습, 지금 쓰는 대안, 근거 수준(봤음, 들었음, 짐작) | 첫 채널과 첫 조사 |
| 출발 경로 | 오픈소스, 앱, 웹 서비스 등과 고른 이유 | 플레이북, 조직, 수집기 |
| 목표와 기한 | 북극성 숫자(예: star 100), 기한, 중간 점검일 | 주기와 도전 판정 |
| 범위 | 할 것, 하지 않을 것 | 업무 생성 제한 |
| 산출물 | 오너가 받게 될 것(배포된 앱, 랜딩 페이지, 게시 초안 묶음, 주간 보고) | 완료 판정 |
| 조직 | 켜진 역할과 이유 | 에이전트 구성 |
| 예산과 사용량 | 현금 상한, 구독 사용 상한(5절) | 예산과 할당량 정책 |
| 금지선 | 절대 하지 않을 일(내 이름으로 글 올리기, 유료 광고 등), 법·규칙 주의 | 정책 엔진의 deny와 강한 승인 |
| 결정 권한 | 오너가 정할 것, CEO가 정하고 알릴 것, 의견만 줄 것 | 승인 정책(`door_policy`) |
| 보고 방식 | Slack 알림 기준, 하루 브리핑 시각, 주간 정리 요일 | 알림과 일정 |
| 성공 조건과 중단 조건 | 이 숫자면 계속, 이 숫자면 멈추거나 방향을 바꿈 | 점검일 판정 |
| 가정 목록 | "우리는 ...라고 믿는다", 중요도, 근거 수준 | 첫 도전들의 순서 |
| 오너 원문 | 대화에서 오너가 한 말 그대로 | CEO가 계획에서 인용 |

칸마다 출처를 표시합니다: **오너가 말함**, **확인함**(CEO가 제안하고 오너가 맞다고 함), **짐작**, **모름**.

### 3.4 지시서가 일을 묶는 방법

- 오너가 승인하면 지시서 1판이 됩니다. 이후 바꿀 때마다 판이 올라가고, 바뀐 줄을 보여 주고 다시 확인합니다.
- CEO의 모든 계획과 도전은 근거가 된 지시서 줄을 인용합니다. 인용할 줄이 없는 일은 시작하지 않고 오너에게 묻습니다.
- 지시서의 예산과 범위 안에서 하는 작은 실험은 CEO가 정하고 활동 기록과 브리핑으로 알립니다.
- 출발 경로, 금지선, 예산, 성공 조건을 바꿔야 할 때만 CEO가 "지시서 변경 제안"을 올립니다. 오너가 승인하기 전에는 그
  부분을 바꾸지 않습니다.
- 오너에게 올리는 결정은 **결정 카드** 모양입니다. 관련 숫자, 대안마다 근거와 위험, CEO 권고, 승인하면 바로 일어날 일,
  되돌릴 수 있는지가 한 화면에 나옵니다.

### 3.5 근거의 기준

초기 사업에서는 객관적으로 확인된 근거를 얻기 어렵습니다(오너 결정, 2026-11-03). 그래서 근거 확인 여부를 일의 관문으로
쓰지 않습니다. 회사는 그때 구할 수 있는 합리적인 근거로 판단하고 진행하되, 판단마다 근거의 확신도(검증된 사실, 출처 있음,
가정, 짐작)를 옆에 보여 줍니다. "검증된 사실" 승격 규칙은 그대로 둡니다. 서버 확인과, 작성자와 다른 역할의 검토가 모두
있어야 합니다. 모델이 같아도 됩니다.
- 점검일과 주기 끝에는 짧은 재정렬 대화를 합니다(최대 5턴. 무엇이 놀라웠나, 숫자는 그대로인가, 금지선과 권한은 그대로인가).

## 4. 운영 루프

```

**도전 회고.** 도전이 끝나면 숫자만 보고하지 않고, 왜 그렇게 됐는지를 정해진 모양으로 판단합니다.

| 칸 | 내용 |
|---|---|
| 가설 | 이 도전이 확인하려던 것(지시서 줄 인용) |
| 관측 | 관심 → 첫 가치 → 반복 사용 단계별 숫자와 관측 기간, 빠진 데이터 |
| 원인 후보 | 숫자가 움직인(또는 안 움직인) 이유 후보와 각각의 근거·확신도. 예: 방문은 늘었는데 설치가 없다 → 설치 과정 문제인가, 대상이 틀렸나 |
| 반대 근거 | 원인 후보를 약하게 하는 사실 |
| 판정 | 계속, 중단, 변경 중 하나와 이유 |
| 다음 제안 | 다음 도전 후보 1~3개. 지시서 범위 안이면 CEO가 고르고, 범위를 넘으면 결정 카드로 올립니다 |

회고에서 나온 교훈은 요약문으로 끝내지 않습니다. 다음 실행에 적용되는 규칙(프롬프트 규칙, 점검표, 평가 사례)으로 남기고,
같은 실수가 반복되는지 다음 회고에서 확인합니다.
사업 (업무 지시서 · 출발 경로 · 북극성 숫자)
 └ 주기 (1~2주) ── 시작: 도전 고르기 / 끝: 숫자로 회고 + 재정렬 대화
     └ 도전 (가설 · 채널 · 목표 숫자 · 시간/사용량 한도 · 멈출 조건)
         ├ 만들기: CPO → 개발 → 배포 ............ 첫 배포는 강한 승인, 이후에는 상시 승인
         ├ 알리기: Growth가 게시 묶음을 준비 → 오너 할 일 → 오너가 게시하고 링크 입력 → 반응 수집
         ├ 응대:   받은 메일 → 분류와 답장 초안 → 승인 → 자동 발송 → 고객 단계 갱신
         └ 재기:   경로 수집기 → 도전 회고 → 다음 도전 제안
매일: Slack 브리핑 (바뀐 것, 숫자, 오너가 할 일, 결정할 것)   매주: 북극성 추이와 도전별 결과
```

## 5. 밖으로 나가는 일의 규칙

| 일 | 누가 | 방식 |
|---|---|---|
| 메일 보내기 | 회사 | 승인되면 Gateway가 자동으로 보냅니다. 같은 템플릿을 반복해서 보낼 때는 "이번 주, 이 템플릿, 최대 N통" 같은 상시 승인을 쓸 수 있습니다. |
| 메일 읽기 | 회사 | 받은 메일을 분류합니다(문의, 버그, 협업, 스팸). 답장 초안과 고객 기록을 만듭니다. |
| 커뮤니티 게시 | **오너** | 회사가 게시 카드를 만듭니다: 어디(링크, 그 커뮤니티의 규칙 요약), 무엇, 언제(추천 시각), 왜(이 도전의 가설). 오너가 올리고 게시 링크를 붙이면, 그 뒤 반응(점수, 댓글, 유입)은 회사가 추적합니다. "무엇"의 모양은 채널마다 다릅니다(아래). |
| 배포 | 회사 | 처음에는 강한 승인, 같은 대상에 다시 배포할 때는 상시 승인입니다. |
| 오너 알림 | 회사 | Slack입니다. 막힌 결정, 실패, 오너 할 일, 하루 브리핑을 보냅니다. 같은 일로는 한 번만 보냅니다. |
| 돈 쓰기, 계약, 개인정보 공유 | 오너 | 지금 정책 그대로입니다(강한 승인 또는 거부). |

**채널마다 회사가 쓸 수 있는 범위가 다릅니다.** 플레이북의 채널마다 `draft`와 `outline` 중 하나를 둡니다.

| 모드 | 회사가 주는 것 | 채널 |
|---|---|---|
| `outline` | 꼭 넣을 사실, 받을 만한 질문과 답할 거리, 점검표, 올릴 시각. **문장은 주지 않습니다.** 오너가 자기 말로 씁니다 | Hacker News, Show HN, Product Hunt, dev.to, LinkedIn, Lobsters, GeekNews. Reddit과 X도 `outline`이지만 규칙을 읽지 못해 회사가 쓰지 않습니다 |
| `draft` | 제목과 본문 초안. 오너가 고쳐서 올립니다 | Hashnode, GitHub 릴리스. 뉴스레터 투고와 Awesome List PR도 `draft`이지만 규칙을 읽지 못해 회사가 쓰지 않습니다 |

규칙을 원문에서 읽은 채널(규칙 확인됨)에만 회사가 씁니다. 읽지 못한 채널(규칙 미확인)에는 카드를 만들지 않습니다
(`docs/design/channel-rules.md`).

**꾸준한 알리기 (오너 지적, 2026-11-03).** 게시물은 금방 묻히므로 알리기는 한 번으로 끝나지 않습니다. 그러나 같은 글의 반복은
막힙니다. HN FAQ: "If a story has not had significant attention in the last year or so, a small number of reposts is ok.
Otherwise we bury reposts as duplicates." Show HN: "New features and upgrades ... generally aren't substantive enough to be
Show HNs. A major overhaul is probably ok." (2026-11-03 원문 확인.) 그래서 다음 구조로 합니다.

- 같은 글이 아니라 새 거리(큰 기능, 이정표, 사용 사례, 만든 이야기, 튜토리얼)로 올립니다. 제품 도전의 결과가 다음 게시 거리가 됩니다.
- 채널을 돌아가며 씁니다. 채널 목록에 다시 올리기 규칙, 최소 간격, 새 내용 필요 여부, 근거 링크를 둡니다.
- 알리기는 정기 업무입니다. 매주 "쉬는 기간이 끝났고 새 거리가 있는 채널"에 대해 게시 카드를 만들어 오너 할 일로 올립니다.
  거리가 없으면 만들지 않고 브리핑에 적습니다. 주당 게시 수 상한을 둡니다.
- 도전은 "무엇이 통하나"(채널, 글 종류, 시각)를 시험하고, 이긴 방식을 정기 업무에 반영합니다. 반응 없는 채널은 뺍니다.
- 게시 링크마다 점수, 댓글, 유입을 추적해 회고에 넣습니다.

어느 채널이든 다음은 제품에 넣지 않습니다: 투표·star 부탁, 리뷰 보상, 자동 게시, 자동 DM. 이것은 이 제품의 규칙입니다.
채널이 글로 금지하는 범위는 서로 다릅니다. Hacker News, Show HN, GeekNews는 투표 부탁을 금지합니다(원문 확인함). GitHub 이용 규칙은
star나 팔로우를 자동으로 늘리는 일과 가짜 계정으로 하는 활동을 금지하고, 사람이 부탁하는 일을 금지한다는 문장은 읽지 못했습니다
(정정: 앞 판은 "GitHub이 부탁을 금지한다"고 적었습니다). Apple, Google Play, Chrome Web Store, LinkedIn의 해당 규칙은 부록 A를 봅니다.
채널별 다시 올리기 규칙, 최소 간격, 출시 관문은 `config/channels.yaml`에 있고, 한국 채널(GeekNews 포함)은 보조입니다.

## 6. 구독 사용량 설정

구독 한도는 CLI가 숫자로 알려 주지 않습니다. 그래서 회사가 자기 사용량을 재고, 사용자가 상한을 정합니다.

- **설정.** 쓰는 구독(예: Claude Max 20x, ChatGPT 플랜), 이 회사가 쓸 비율이나 상한(일·주 단위, 토큰 또는 USD 환산),
  역할별 모델(일상 운영은 가벼운 모델, 시작 대화·결정·회고는 큰 모델).
- **우선순위.** 상한에 가까워지면 시작 대화, 오너 결정, 메일 응대를 먼저 하고, 조사와 정기 작업은 미룹니다.
- **상한에 닿으면.** 실패가 아니라 대기입니다. Slack으로 알리고, 다음 기간에 이어 갑니다(BACKLOG A2와 같은 방식).
- **보여 주기.** 사용량 화면과 주간 정리에 "이번 주 상한 대비 사용, 역할별 사용, 도전당 사용"이 나옵니다.

## 7. 규칙은 설정 화면에서 받습니다 (오너 결정 8)

외부로 나가는 규칙과 연결 정보는 코드나 CLAUDE.md에 고정하지 않습니다. 사용자가 설정 화면에서 넣고 바꿉니다.
오픈소스 사용자마다 쓰는 구독, 계정, 감수할 위험이 다르기 때문입니다.

| 설정 묶음 | 칸 | 기본값 |
|---|---|---|
| 구독과 사용량 | 쓰는 구독, 일·주 상한, 역할별 모델, 상한 도달 시 동작 | 상한 없음이 아니라 "구독의 절반"처럼 보수적인 값. 첫 실행 때 묻습니다 |
| 커넥터별 모드 | 메일, Slack, 배포마다 `꺼짐` / `outbox` / `승인 후 자동` | 모두 `outbox` |
| 연결 정보 | Slack 봇·앱 토큰, Gmail OAuth, GitHub 토큰, Cloudflare 토큰 | 비어 있음. 비어 있으면 그 커넥터는 꺼집니다 |
| 승인 규칙 | 행동 종류별 `auto` / `approve` / `strong_approve` / `deny`, 상시 승인 상한 | 지금의 `config/tool_policy.yaml` |
| 알림 | Slack 채널, 알릴 일의 종류, 하루 브리핑 시각, 조용한 시간 | 막힌 결정과 실패만 알림, 브리핑 09:00 |

지켜야 할 바닥 규칙은 설정으로 끌 수 없습니다.

- 모델이 정책 모드를 정하지 못합니다. 서버만 정합니다.
- 연결 정보는 명령줄과 로그에 남기지 않습니다. 화면에는 끝 4자리만 보여 줍니다.
- `external.pii_share` 같은 deny 항목은 설정에서도 auto로 올릴 수 없습니다. `strong_approve`가 가장 낮은 단계입니다.
- 설정 변경은 활동 기록에 남습니다.

CLAUDE.md의 하드 제약 두 줄은 이 구조에 맞게 고칩니다. 아래는 제안 문구이고, 오너가 확인한 뒤에 반영합니다.

- "External connectors stay in outbox or dry-run mode." →
  "External connectors default to outbox. Only the owner turns a connector live, in Settings."
- "Never add API keys or API-key code paths." →
  "Never add LLM API keys or API-key code paths. Connector credentials (Slack, Gmail, GitHub, Cloudflare) come from
  Settings and are never printed, logged, or passed on a command line."

| P0 | 오너 할 일 | 게시 카드 하나가 오너 게시 → 링크 입력 → 반응 추적까지 돕니다 |
| P0 | 도전 루프: 도전→실행 연결, GitHub 수집기, 3단 지표, 도전 회고, 다음 도전 제안 | 위 완료 기준 문장이 한 번 참이 됩니다 |

| P3 | 두 번째 출발 경로 | 다른 경로의 사업 하나가 같은 틀로 시작됩니다 |

## 11. 오너 아이디어함 (오너 요청, 2026-11-03)

회사가 일하는 동안 오너에게 그 사업에 대한 새 기능, 다른 방법, 개선점이 떠오를 수 있습니다. 이를 언제든 던져 넣는 창구입니다.
오너는 정리하지 않고 생각나는 대로 적습니다. 읽고, 반영하고, 버리고, 다시 짜는 일은 CEO가 합니다.

**넣기.** 사업 화면과 모든 화면의 머리줄에 있는 "아이디어 남기기"에서 사업을 고르고 한 줄부터 몇 문단까지 적습니다.
나중에는 Slack으로도 받습니다. 붙인 링크나 자료도 같이 남길 수 있습니다.

**CEO의 처리.** 아이디어가 들어오면 CEO가 곧바로(사용량 상한 안에서) 읽고, 지시서와 지금 도전들에 비춰 다음 중 하나로 처리합니다.

| 처리 | 뜻 | 누가 정하나 |
|---|---|---|
| 지금 반영 | 진행 중인 도전의 범위 안이면 업무로 넣습니다 | CEO가 하고 알림 |
| 도전 후보 | 새 도전 후보로 만들어 다음 고르기 때 올립니다 | CEO가 하고 알림 |
| 합침 | 이미 있는 도전이나 후보와 같은 생각이면 그쪽에 붙입니다 | CEO가 하고 알림 |
| 다시 짬 | 아이디어를 쪼개거나 더 작은 시험으로 바꿔 위의 처리로 보냅니다 | CEO가 하고 알림 |
| 지시서 변경 제안 | 출발 경로, 금지선, 예산, 성공 조건을 건드리면 결정 카드로 올립니다 | 오너 |
| 보류 | 지금은 아니지만 나중에 쓸모 있을 것. 점검일이나 회고 때 다시 봅니다 | CEO가 하고 알림 |
| 버림 제안 | 지시서와 맞지 않거나 근거가 약하다고 보면, 버리자는 이유를 보고합니다. 실제로 버리는 것은 오너만 합니다 | 오너 |

모든 처리에는 이유 한두 줄과 연결된 지시서 줄, 도전, 업무가 붙습니다. 오너는 처리 결과를 보고 한 번에 뒤집을 수 있습니다
("이건 버리지 말고 후보로"). 뒤집은 결과는 회사 기억에 오너 선호로 남아, 다음 처리 때 CEO가 참고합니다.

**보이기.** 아이디어함은 머리줄 "**아이디어** · 처리 대기 1 · 이번 주 5"와 목록입니다. 각 줄에 처리 결과 배지, 이유, 연결이 붙습니다.
하루 브리핑과 주간 정리에는 "오너 아이디어 n건: 반영 a, 후보 b, 보류 c, 버림 d"가 들어갑니다.

## 12. 사람 명단과 만나기 (전문가 패널 반영, 2026-11-03)

첫 100명은 게시판 반응이 아니라 창업자가 한 명씩 만나는 데서 나옵니다(09 2절 1번, 조사 문서 1절). 회사는 사람을 찾고, 메모와 질문을
준비하고, 기록합니다. 연락은 오너가 자기 계정, 자기 말로 합니다.

**명단.** 사람마다 이름이나 아이디, 어디서 찾았나(출처), 왜 이 사람인가, 단계(찾음 → 연락함 → 대화함 → 첫 가치 → 반복 사용),
그 사람이 한 말 인용, 다음 할 일과 날짜를 둡니다. 북극성 숫자와 3단 지표는 이 명단에서 셉니다.

**사람을 찾는 곳.** 아는 사람이 없어도 시작할 수 있습니다(오너 지적).

| 출처 | 회사가 하는 일 | 오너가 하는 일 |
|---|---|---|
| 아는 사람(있으면) | 시작 대화에서 받은 이름에 연락 이유와 첫 질문을 붙임 | 직접 연락 |
| 문제를 공개적으로 말한 사람 | 관련 GitHub issue, Reddit·HN·Stack Overflow 질문, 포럼 글에서 "이 문제를 겪는다"고 쓴 사람을 공개 정보로만 찾음. 링크와 그 사람이 쓴 문장을 붙임 | 그 글에 도움이 되는 답을 직접 달고, 필요하면 1:1로 연락 |
| 비슷한 도구 사용자 | 경쟁·대체 도구의 issue와 토론에서 불편을 말한 사람을 찾음 | 위와 같음 |
| 커뮤니티 참여 | 오너가 도움을 줄 수 있는 질문 글을 주 3~5개 골라 줌(링크만, 홍보 없음) | 자기 지식으로 답함 |
| 들어온 사람 | 가입, 설치, issue, 메일, 게시 댓글로 들어온 사람을 명단에 자동으로 넣음 | 첫 답은 직접 |

이메일 주소를 긁어 모으지 않고, 대량 메시지를 보내지 않습니다. 각 플랫폼 규칙 안에서 공개된 대화에 참여하는 것이 기본입니다.

**오너 할 일 종류 추가.** 연락, 같이 설치·데모, 후속 연락(날짜), 소개 부탁(첫 가치를 본 사람에게 "이게 필요한 사람 또 있어요?"),
참여(남의 글에 도움 댓글). 하루 브리핑에 "오늘 연락하거나 다시 연락할 사람 3명"이 나옵니다.

**판정.** 첫 100명까지 도전의 성공은 관심(star)이 아니라 첫 가치와 반복 사용으로 판정합니다. 회고는 사용자가 30명 미만이면
사람별 인용 세 줄(무엇을 했나, 사용자가 뭐라 했나, 다음)로 합니다.

**완료 기준(8절 대체).** "외부 사용자 N명이 두 번 이상 썼고, 그중 M명과 오너가 직접 대화했다." N과 M은 시작 대화에서 정합니다.

**출시 관문.** Show HN, Product Hunt 같은 한 번뿐인 큰 출시는 녹화 데모, 외부인 3명의 새 PC 설치 성공(시간 측정),
README 첫 화면 점검, 명단에서 첫 가치에 닿은 사람 20명이 갖춰진 뒤에만 카드를 만듭니다.

**글로벌 우선(오너 결정 17).** 첫 채널은 글로벌(영어)입니다. 관련 서브레딧과 디스코드 참여, dev.to 같은 개발 블로그, X, GitHub(Awesome
List 등)으로 시작하고, 관문을 넘으면 Show HN을 한 번 합니다. 한국어 채널(GeekNews Show, 디스콰이엇 등)은 같이 쓰되 보조입니다.
