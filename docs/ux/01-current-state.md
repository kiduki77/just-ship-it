## 3. 객체와 상태 전이

콘솔이 보여 주는 객체는 8종이고, 대부분 상태 기계를 가집니다.

**프로젝트(P-n)**

```
CREATED → RUNNING ─┬─ phase: planning → executing → ceo_review ─┬→ (follow_up) executing …
                   │                                             ├→ meeting → deciding
                   │                                             └→ deciding → DONE (phase done)
                   ├─ WAITING_HUMAN   차단 요청이 있을 때. 결정되면 RUNNING으로 돌아감
                   └─ FAILED          예산 초과(BudgetExceeded) 등. CLI로 재실행
아무 상태에서 → ARCHIVED (오너가 보관. 대기 요청은 CANCELLED)
```

**업무(T-n)**
`PROPOSED → READY → RUNNING → REVIEW → (REWORK → RUNNING)* → DONE`.
그 밖의 분기: `APPROVAL_REQUIRED → APPROVED | REJECTED`, `FAILED`, `CANCELLED`(오너 지시로 재정렬될 때).

**요청(REQ-n)**
`PENDING → APPROVED | ANSWERED | DEFERRED | REJECTED`.
시스템이 바꾸는 상태: `AUTO_APPROVED`, `DENIED_BY_POLICY`, `EXPIRED`(만료 후에는 반려와 보류만 가능), `CANCELLED`(병합, 철회, 보관).
- 정책 모드: `auto`, `approve`, `strong_approve`(요청 번호를 직접 입력), `deny`.
- 종류: APPROVAL, QUESTION, PROPOSAL, RESOURCE, SKILL, ESCALATION, DEVELOPMENT, CLARIFICATION.
- 차단(blocking) 요청은 프로젝트를 WAITING_HUMAN으로 멈춥니다.

**근거(EV-n)**
상태 기계 대신 두 축으로 분류합니다.
- 종류: verified_fact, sourced_claim, calculation, assumption, hypothesis.
- 검증: unchecked, url_ok, quote_found, supported, weak, contradicted, unverifiable, url_unreachable, reproduced, computed, deterministic, transcribed, derived.
- 검증된 사실은 서버 검증과 다른 모델 계열의 검토를 함께 통과해야만 될 수 있습니다.

**결정(DEC-n)**
- 판정: adopt, conditional, defer, reject.
- 상태: `PENDING_APPROVAL → EFFECTIVE → SUPERSEDED`.

**회의(M-n)**
입장 발표, 반박 라운드, CEO 결정(DEC) 순서로 진행합니다.

**명세(spec)**
`DRAFT → IN_REVIEW → SPEC_APPROVED → READY_FOR_DEV → IN_DEVELOPMENT → DELIVERED → ACCEPTED → MERGED`.
분기: `CLARIFICATION_REQUIRED`, `REJECTED`.

**개발 작업(J-n)**
`QUEUED → INTAKE → PLAN_REVIEW → IMPLEMENTING → QA → REVIEWING → SHIPPING → DELIVERED → MERGED`.
분기: `CLARIFICATION_REQUIRED`, `FAILED`.

**스킬**
`GAP_DETECTED → PROPOSED → CANDIDATE → EVALUATING → (EVAL_FAILED) → AWAITING_APPROVAL → ACTIVE → DEPRECATED`.
분기: `REJECTED`.

**오너가 개입하는 전이**
- 요청 결정. 차단 요청이 풀리면 프로젝트가 재개되고, 메모와 답변은 아직 시작하지 않은 업무를 재정렬합니다.
- 명세 승인. 개발 작업이 시작됩니다.
- 머지 승인(강한 승인). 결과가 제품 저장소에 들어갑니다.
- 프로젝트 보관.
- 예산 변경과 재실행(지금은 CLI 전용).

## 4. 화면 간 관계

```
대시보드 ─┬→ 승인 센터?req=…       (결정 대기 항목)
          ├→ 프로젝트 개요          (카드)
          └→ 조직도
프로젝트 개요 ─→ 승인 탭?req=…  ─→  업무 보드?task=…  ─→ 근거 원장?ev=…
요청 본문의 EV/T/REQ 표기 → 각 화면으로 링크 (같은 출처 링크만 앱 안에서 이동)
개발팀 ─→ 프로젝트 개발 탭
```

**같은 화면이 두 곳에 있습니다.** 승인, 개발, 팀(조직도)은 회사 메뉴와 프로젝트 탭 양쪽에 있습니다. 둘 다 같은 컴포넌트를 범위만 바꿔 씁니다.
그래서 같은 요청에 들어가는 URL이 `/approvals?req=` 와 `/projects/5/approvals?req=` 두 가지입니다.

- 결정 대기 히어로.
- 문구로 승인 여부를 추측하지 않는 결정 규칙.
