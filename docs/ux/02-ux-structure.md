# 02. UX 구조

## 1. 사용자 역할

| 역할 | 누구 | 콘솔에서 하는 일 |
|---|---|---|
| **오너** (유일한 사람 사용자) | 자기 PC에서 자기 Claude·Codex 구독으로 AI 회사를 돌리는 1인 창업가·개발자 | 결정, 지시, 현황 파악, 결론의 신뢰도 판단, 복구 |
| AI CEO | 에이전트 | 계획을 세우고, 검토하고, 회의를 소집하고, 최종 결정을 내립니다. 결정 요청도 올립니다. |
| 본부 에이전트 | 조사, 전략, 재무, 제품, 마케팅, 분석 | 업무를 하고, 근거를 남기고, 요청을 올립니다. |
| 검토자 | 다른 모델 계열(리스크·감사, 코드 리뷰어) | 독립 검토를 하고 반론을 냅니다. |
| 개발팀 | 엔지니어(격리 컨테이너, pstack) | 명세를 구현하고 머지 승인을 요청합니다. |
| 정책 엔진 | 시스템 | 자동 승인, 금지, 만료를 처리합니다. |

사람 사용자는 오너 한 명이고, 권한 구분이나 보기 전용 공유는 범위 밖입니다. 오픈소스로 공개해도 사용자 프로필은 같습니다.
에이전트는 사용자가 아니라 **화면에 나오는 행위자**이므로, 어떤 주장이든 누가 했는지와 누가 검토했는지를 함께 보여 줍니다.

**방문 장면.** 오너는 작업을 지켜보지 않습니다. 하루에 몇 번, 주로 데스크톱 브라우저로 들어와서 다음 네 가지를 확인합니다.
1. 나를 기다리는 것
2. 지난번 이후 바뀐 것
3. 막힌 것과 그 이유
4. 믿어도 되는 결론

들어와서 할 일을 다 할 때까지 대략 몇 분 정도라고 가정합니다. 이 가정은 05에서 측정해 확인합니다.

## 2. 핵심 업무 시나리오

시나리오마다 **성공 기준**을 두고, 05에서 현재 값과 목표 값을 잽니다.

| ID | 시나리오 | 시작 | 끝 | 성공 기준 |
|---|---|---|---|---|
| S1 | 차단 요청 해제 | 콘솔 첫 화면 | 결정이 기록되고 프로젝트가 재개됨 | 첫 화면에서 결정 화면까지 1클릭. 무엇을 결정하는지와 승인 시 결과가 스크롤 없이 보임. 결정 버튼이 항상 화면 안에 있음 |
| S2 | 질문에 답변 | 결정함 | 답변 기록, 재정렬 결과 확인 | 선택지를 고르거나 직접 쓰기. 답변이 어떤 업무를 바꿨는지 같은 화면에서 확인 |
| S3 | 강한 승인(머지, 공개) | 결정함 | 번호 입력 후 승인 | 무엇이 바뀌는지(대상 저장소, 브랜치, 수용 기준 충족 여부)를 승인 전에 봄. 잘못된 승인 0건 |
| S4 | 돌아와서 현황 파악 | 콘솔 첫 화면 | "이상 없음" 또는 다음 행동 결정 | 프로젝트마다 단계, 멈춘 이유, 지난 방문 이후 변화가 첫 화면에 나옴 |
| S5 | 결론 신뢰 판단 | 결정(DEC) 또는 요청 | 근거별 확신도 확인 | 결론 옆에서 근거의 종류와 검증 상태 분포를 바로 봄. 근거 하나는 그 자리에서 펼쳐 봄(화면 이동 없음) |
| S6 | 지시 남기기와 반영 확인 | 프로젝트 | 지시 기록, 재정렬 결과 | 결정 없이도 지시를 남길 수 있음(지금은 요청에 붙인 메모로만 가능). 지시 뒤 취소, 수정, 추가된 업무가 보임 |
| S7 | 새 사업 목표 맡기기 | 아무 곳 | 프로젝트 생성, 계획 단계 시작 | 목표와 예산(선택)을 입력. 생성 후 그 프로젝트로 이동 |
| S8 | 멈춘 프로젝트 복구 | 실패하거나 멈춘 프로젝트 | 재실행 | 멈춘 이유와 복구 동작(예산 변경 후 재실행, 재시도)이 같은 곳에 있음. CLI 불필요 |
| S9 | 개발 작업 추적 | 프로젝트 또는 개발팀 | 머지 결정 | 파이프라인 위치, 실패 이유, 수용 검수 결과가 한 화면에 있음 |

## 3. 동선

### S1: 차단 요청 해제 (가장 중요)

```
홈 ─ "나를 기다리는 결정" 1순위 항목 클릭
  └→ 결정함 /inbox/REQ-66
       [결정 요약]  한 줄 요청 · 요청자 · 프로젝트 · 차단 여부 · 만료
       [선택지별 결과] 승인 → P-5 재개, CEO 최종 결정 확정 / 반려 → … / 보류 → …
       [근거 확신도] 인용 근거 12개: 검증 3 · 출처 6 · 가설 3   (항목을 펼치면 각 EV)
       [결정 바]  항상 보임: 선택지 · 메모 · 승인/반려/보류
       [전문]     요청 내용과 근거 전문(접힘, 펼쳐 읽기)
  → 결정 → 영수증(무슨 일이 시작됐는지) → "다음 결정 REQ-64 →"
```

### S4: 돌아와서 현황 파악

```
홈
  ├ 나를 기다리는 결정 (차단 우선)
  ├ 지난 방문 이후      완료된 업무 3 · 새 결정 1 · 새 요청 2 · 실패 0   → 각 항목 링크
  └ 프로젝트 상태 줄    P-5 ● 오너 대기 · 결정 단계 · REQ-66이 막고 있음 · 업무 19/19 · $57/$80
                       P-7 ● 실행 중 · 업무 4/9 · 시장조사 T-71 진행 중
                       P-8 ● 실패 · 예산 한도 도달 → [예산 조정 후 재실행]
```

### S5: 결론 신뢰 판단

```
프로젝트 › 결정 DEC-4
  판정 조건부 · 유효
  근거 확신도 막대  ■■■□□□□□  검증 3 · 출처 4 · 가설 2 · 가정 1 · 반박 0
  찬성 근거 칩 [● EV-1604 검증] [○ EV-1587 출처] …  ← 칩을 열면 주장·인용·출처·검토 메모를 그 자리에서 봄
  반대 근거 칩 …
  회의 M-3 기록 (이 결정을 낳은 회의)
```

### S6: 지시와 반영

```
프로젝트 개요 ─ [지시 남기기] (어느 요청에도 묶이지 않는 오너 지시)
  → 기록 → 재정렬 진행 중 → "취소 T-58 · 수정 T-59 · 추가 T-71" 카드가 개요 상단 "오너 지시와 반영"에 나옴
```

S6의 "요청에 묶이지 않는 지시"는 백엔드 기능이 새로 필요합니다(05 참조). 오너가 이 범위를 승인해야 진행합니다.

### S8: 복구

```
프로젝트 헤더의 상태 줄: ● 실패 · 예산 한도($40) 도달 · 결정 단계에서 멈춤
  [예산 조정 후 재실행]  → 화면 안에서 새 한도 입력 → 확인 → 재실행이 대기열에 들어감 → 상태 줄이 "실행 중"으로 바뀜
```

## 4. 정보 구조(IA)

### 원칙

1. **객체마다 기준 주소는 하나입니다.** 같은 요청에 URL이 두 개 있는 지금의 구조를 없앱니다. 범위는 화면 복제 대신 필터로 표현합니다.
2. **첫 화면은 오너의 할 일입니다.** 대시보드 지표보다 결정 대기, 변화, 막힌 곳이 먼저입니다.
3. **프로젝트 탭은 질문 단위로 나눕니다.** 데이터 테이블 단위로 나누지 않습니다. 탭은 9개에서 6개로 줄입니다.
4. **회사 관리 화면은 뒤로 뺍니다.** 조직, 개발팀, 스킬, 자동화, 사용량은 핵심 세 업무가 아니므로 두 번째 그룹으로 둡니다.

### 사이트맵

```
홈                       /                         오너의 할 일 · 지난 방문 이후 · 프로젝트 상태
결정함                   /inbox                    대기(차단 우선) · 처리됨(의미 있는 것만) · ?project= 필터
  └ 요청                 /inbox/:reqId             결정 화면 (기준 주소)
프로젝트                 /projects                 전체 목록 (보관, [TEST] 필터)
  └ P-n                  /projects/:id             개요: 상태 줄 · 다음 단계 · 오너 지시와 반영 · 핵심 결정 · 계획 요약
     ├ 업무              /projects/:id/tasks       보드 + 오른쪽 상세 패널 (?task=)
     ├ 결정              /projects/:id/decisions   결정(DEC) 목록 · 결정마다 근거 확신도 · 연결된 회의(M) 기록
     ├ 근거              /projects/:id/evidence    원장 (?ev=, 필터를 URL에 보존)
     ├ 문서              /projects/:id/docs        최종 보고서(맨 위 고정) + 산출물
     └ 개발              /projects/:id/dev         명세 · 개발 작업 (J 상세는 기준 주소로 링크)
회사
  ├ 조직                 /company/org              조직도 (?project= 범위)
  ├ 개발팀               /company/engineering      전체 명세 · 개발 작업
  │  └ 개발 작업         /company/engineering/jobs/:jobId   J-n 기준 주소
  ├ 스킬                 /company/skills
  ├ 자동화               /company/automation       정기 업무 · KPI · 외부 실행 기록 (지금의 "운영")
  └ 사용량               /company/usage
```

**바뀌는 것**
- 프로젝트 탭 "승인"은 없어지고 `/inbox?project=5`로 갑니다. 개요의 대기 배너도 그쪽으로 연결합니다.
- 탭 "회의실"은 "결정"에 합칩니다. 회의는 결정을 만드는 과정이기 때문입니다.
- 탭 "보고서"와 "산출물"은 "문서"로 합칩니다.
- 탭 "팀"은 `/company/org?project=5`로 옮깁니다. 개요에는 "지금 일하는 에이전트" 한 줄만 남깁니다.
- 지금 URL은 새 URL로 넘깁니다(리다이렉트). 요청, 근거, 업무에 걸린 기존 링크는 깨지지 않습니다.

### 내비게이션 모델

- **사이드바(고정).**
  - 홈, 결정함(대기 수 표시, 차단이 있으면 강조), 프로젝트(진행 중인 것 목록과 상태 점)를 둡니다.
  - 그 아래 접을 수 있는 "회사" 그룹을 두고, 맨 아래에 연결 상태를 둡니다.
- **ID 바로가기.** `Ctrl+K`(또는 `/`)로 `REQ-66`, `T-58`, `EV-1604`, `DEC-4`, `J-7`, `P-5`를 입력하면 그 객체의 기준 주소로 갑니다.
  본문에 나오는 같은 ID 표기도 모두 같은 주소로 연결합니다.
- **기본-상세(primary-detail).** 결정함, 업무, 문서, 개발 작업은 왼쪽 목록과 오른쪽 상세를 같은 화면에 둡니다. 상세가 아래로 열리면서 스크롤이 튀는 일이 없습니다.
- **상태 보존.** 필터, 선택, 탭은 URL에 담습니다. 뒤로 가기와 새로고침에도 같은 화면이 나옵니다.

### 객체별 기준 주소

| 객체 | 기준 주소 | 본문 표기 |
|---|---|---|
| P-n | `/projects/:id` | P-5 |
| T-n | `/projects/:id/tasks?task=:n` | T-58 |
| REQ-n | `/inbox/:n` | REQ-66 |
| EV-n | 그 자리에서 펼치는 근거 미리보기. 전체는 `/projects/:id/evidence?ev=:n` | EV-1604 (종류 표시 + 검증 색) |
| DEC-n | `/projects/:id/decisions#dec-:n` | DEC-4 |
| M-n | `/projects/:id/decisions#m-:n` | M-3 |
| J-n | `/company/engineering/jobs/:n` | J-7 |
| spec | `/company/engineering?spec=:key` | AICOMP-0001 |
