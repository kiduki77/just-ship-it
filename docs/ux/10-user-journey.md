# 10. 사용자 여정: 사업 만들기부터 운영까지

2026-11-06 작성. 1인 창업자가 Just Ship It을 처음 켜서 사업을 굴리기까지 겪는 모든 순간을 순서대로 적고,
순간마다 지금 실제로 일어나는 일과 끊기는 지점을 표시한다.

- 🔴 **확인됨**: 2026-11-06 오너가 실제로 쓰다가 겪었거나 코드와 로그로 확인한 끊김.
- 🟡 **의심**: 화면과 코드로 보아 끊길 것 같지만 아직 사람이 겪지 않은 지점. 가상 첫 사용자 테스트로 확인한다.
- ✅ **고침**: 같은 날 고쳐서 main에 들어간 것. 🛠 **고치는 중**: 사이클 단계 작업(`feat/cycle-stages`)에 들어 있는 것.

모든 순간에서 사용자는 네 가지를 바로 알 수 있어야 한다. 이것이 이 문서의 판정 기준이다.

1. **지금 무슨 일이 일어나고 있나** (회사가 하는 일, 누가, 얼마나 걸리나)
2. **왜 그 일을 하나** (내가 승인한 무엇 때문인가)
3. **내가 할 일이 있나** (있다면 무엇을, 언제까지)
4. **다음에 무엇이 오나** (이 일이 끝나면, 멈추면)

## 0. 설치하고 처음 켜기

| | |
|---|---|
| 기대 | 명령 몇 줄로 켜지고, 열자마자 무엇을 하면 되는지 보인다. |
| 지금 | `docker compose up -d`, `uv sync`, 콘솔 빌드, `ship init`, 샌드박스 빌드, `ship supervise`. 터미널에 찍힌 로그인 주소를 10분 안에 열어야 한다. |

- 🔴 **egress 프록시가 안 떠 있어도 아무도 말해 주지 않는다.** pull로 새 서비스가 들어왔는데 컨테이너가 없었고, 코드 읽기가
  2초 만에 실패했다. 원인은 워커 로그에만 있었다. → 콘솔에 **시스템 상태** 표시(Docker, egress, 샌드박스 이미지, Claude 로그인,
  워커)와 각각의 해결 명령. 시작할 때 한 번 점검하는 `doctor` 명령.
- 🔴 ✅ **워커를 따로 켜야 했고, Ctrl+C로 깔끔하게 안 꺼졌다.** `supervise` 하나로 묶고 종료를 고쳤다.
- 🔴 **재시작하니 오류가 났다.** 작업 중인 코드를 실행 폴더에서 고친 탓이었다(개발 과정의 문제, 사용자 문제는 아님). 다만 사용자도
  `git pull` 뒤에 DB 마이그레이션을 안 돌리면 똑같이 깨진다. → 시작할 때 DB 버전이 코드와 다르면 "마이그레이션을 돌려 주세요"를
  화면과 터미널에 말한다.
- 🟡 **로그인 주소가 10분 만에 만료된다.** 놓치면 `ship api --login`을 알아야 한다. 로그인 화면이 그 명령을 보여 주긴 한다.
- 🟡 **첫 화면이 대시보드다.** 사업이 없을 때 "사업을 시작하세요" 카드와 4단계 설명이 나온다. 이것은 괜찮다. 다만 사이드바에
  16개 메뉴가 그대로 보여서, 사업이 하나도 없는데 업무, 프로젝트, 정기 업무, 스킬, 조직도가 다 열려 있다.

## 1. 사업 만들기

| | |
|---|---|
| 기대 | 아이디어나 이미 만든 제품을 넣으면 회사가 받아 든다. |
| 지금 | "새 아이디어" 또는 "이미 있는 제품"을 고른다. 제품은 PC의 git 폴더 경로를 넣는다(GitHub 주소는 거절). 회사는 `products/`에 복사본을 만든다. |

- 🔴 **GitHub 주소를 넣고 싶어 한다.** 지금은 "PC에 clone한 뒤 폴더를 달라"며 거절한다. private 저장소를 읽을 수 있는 길이 이것뿐이라는
  설명이 없어서, 오너는 GitHub 연결을 해 두었는데 왜 안 되는지 모른다. → GitHub 연결이 있으면 그 토큰으로 clone까지 회사가 하거나,
  최소한 "왜 폴더여야 하는지"를 한 줄로 말한다.
- 🟡 **경로를 직접 타이핑해야 한다.** 절대 경로, 저장소 맨 위 폴더, 커밋이 하나 이상 있어야 한다는 조건을 틀릴 때마다 하나씩 알게 된다.
- 🔴 ✅ **가져올 때 작업 중인 브랜치를 그대로 가져갔다.** CEO가 엉뚱한 브랜치 이름을 말했다. → 가져올 브랜치를 보여 주고 고르게 한다(미해결).

## 2. 시작 대화

| | |
|---|---|
| 기대 | CEO와 대화하며 내 사업을 정리한다. CEO가 무엇을 알아냈는지 옆에서 보인다. |
| 지금 | 최대 20개 질문. 오른쪽에 계획(7칸)이 채워진다. 줄마다 "내가 말함", "확인함", "CEO 짐작"이 붙는다. |

- 🔴 ✅ **CEO가 생각하는 동안 아무 표시가 없어서 멈춘 줄 알았다.** 경과 시간, 오래 걸림 안내, 워커 꺼짐 경고를 넣었다.
- 🔴 ✅ **제품 코드 읽기가 실패하면 영원히 실패였다.** 샌드박스 문제는 기다리고, 이유를 보여 주고, 다시 읽기 버튼을 넣었다.
- 🔴 **CEO가 하지 않을 일을 약속했다.** "작업 시작 전에 코드를 다시 읽게 하겠다". 코드 어디에도 그런 동작이 없었다. → 에이전트
  지시문에서 막았고(✅), 에이전트 출력에 "할 수 없는 약속" 검사를 넣는 것이 남았다.
- 🟡 **질문이 몇 개 남았는지와 계획이 얼마나 찼는지가 따로 논다.** "질문 3/20"과 "필수 7칸 중 1칸"이 둘 다 있어서 언제 끝나는지
  가늠이 안 된다. → "필수 칸이 다 차면 끝나요, 지금 2칸 남음"처럼 하나의 진행으로 말한다.

## 3. 계획 승인

| | |
|---|---|
| 기대 | 승인하면 회사가 무엇을 할지 설명하고, 내가 시작을 눌러야 시작한다. |
| 지금 (main) | 승인과 동시에 첫 프로젝트가 만들어지고 실행된다. 화면은 프로젝트 페이지로 넘어간다. 1분 안에 사람 찾기, 스레드 찾기가 저절로 돈다. |

- 🔴 🛠 **승인 뒤가 블랙박스다.** "갑자기 얘가 뭘 하는데 뭘 하는지 모르겠다". → 사이클 단계: 승인하면 CEO가 사이클을 제안하고,
  오너가 시작을 눌러야 첫 단계만 돈다.
- 🔴 🛠 **원하지 않은 일이 돌았다.** 사람 찾기가 돌아서 "이 사람들에게 연락하세요" 할 일이 생겼다. → 기본 차단. 오너가 시작한 단계에
  적힌 일만 돈다.

## 4. 첫 사이클 제안 보고 시작하기 (🛠 사이클 단계 작업)

| | |
|---|---|
| 기대 | "이번 사이클은 이렇게 짰어요" 설명과 단계 목록. 단계마다 회사가 하는 일, 내 일, 예상 시간과 사용량. 시작 또는 고칠 점 말하기. |
| 계획 | 대시보드 맨 위에 제안 카드. CEO가 쓰는 동안은 경과 시간이 도는 대기 표시. |

- 🟡 **개념이 너무 많아진다.** 이미 사업, 계획, 실험, 프로젝트, 업무, 결정, 내 할 일, 정기 업무, 스킬이 있는데 사이클과 단계가
  더해진다. 오너가 "단계"와 "프로젝트"와 "실험"의 차이를 알아야 한다면 실패다. → 화면에서 오너가 만나는 단위를
  **사이클 → 단계 → 업무** 세 층으로 줄이고, 프로젝트와 실험은 단계 안의 세부로 숨긴다(정보 구조 재설계 필요).
- 🟡 **예상 사용량을 오너가 읽을 수 있는 말로.** "$3.20"보다 "구독 하루 사용량의 약 15%"가 오너에게 의미가 있다.

## 5. 단계가 도는 동안 지켜보기

| | |
|---|---|
| 기대 | 대시보드를 열면 10초 안에 "2번째 사이클 · 검증 단계 · 에이전트 3명이 이 일을 하는 중"을 안다. |
| 지금 (main) | 대시보드에 "회사 지금" 카드(일하는 에이전트와 업무 제목), 최근 활동, 최근 업무, 프로젝트 예산. 어느 단계인지는 없다. |

- 🔴 🛠 **어느 에이전트가 어느 단계의 무슨 일을 하는지 안 보인다.** → 단계 막대, 지금 단계 업무 n/m, 에이전트별 작업 카드.
- 🔴 🛠 **일 안 하는 에이전트가 "작업 중"으로 보였다.** 멈춘 프로젝트, 오너 답을 기다리는 개발까지. 리뷰에서 다시 잡았다.
- 🟡 **최근 활동이 기계 언어다.** "Task: Ready → Running", "External action created: crm.interaction_log". 오너 문장이 아니다.
  → 활동 기록을 "시장 조사 에이전트가 가격 조사를 시작했어요"처럼 사람 말로, 또는 대시보드에서는 빼고 활동 화면에만.

## 6. 결정 내리기

| | |
|---|---|
| 기대 | 내가 정할 것만, 권고와 이유와 되돌릴 수 있는지가 한눈에. |
| 지금 | 결정 화면이 4열 보드(지금 결정 / 대기 / 보류 / 최근 결정). 카드마다 권고, 근거, 위험. |

- 🔴 **나쁜 권고가 올라왔다.** 코드를 못 읽자 "저장소를 공개하세요"를 권했다. 근거 칸은 전부 "가정, 미확인"이었다. → 근거가 전부
  가정인 권고는 권고로 내세우지 않고 "회사가 모르는 것"으로 보여 준다.
- 🟡 **보드 4열이 첫 사용자에게 무겁다.** 오너가 할 일은 "지금 결정" 한 열이다. 나머지는 기록이다.
- 🟡 **결정이 어느 단계에 속하는지 안 보인다.** 사이클이 들어오면 "검증 단계 · 이 결정이 끝나야 단계가 진행돼요"가 필요하다.

## 7. 내 할 일 (게시, 연락, 확인)

| | |
|---|---|
| 기대 | 회사가 준비한 것을 내가 직접 올리고, 했다고 표시한다. |
| 지금 | 할 일 보드. 게시 글은 회사가 써 두고, 오너가 올린 뒤 링크를 넣는다. |

- 🔴 🛠 **원하지 않은 할 일이 생겼다.** → 단계가 허용한 종류만 생긴다.
- 🟡 **왜 이 할 일이 생겼는지 거슬러 갈 수 없다.** 어느 단계, 어느 결정에서 나왔는지 카드에 없다.
- 🟡 **할 일과 결정이 두 화면으로 나뉘어 있다.** 오너 입장에서는 둘 다 "내가 해야 하는 것"이다. 대시보드 "오늘 할 일"이 둘을 합치지만,
  사이드바에는 두 메뉴가 따로 있다.

## 8. 단계가 끝나고 다음 단계로 (🛠 사이클 단계 작업)

| | |
|---|---|
| 기대 | "검증 단계가 끝났어요. 한 일, 쓴 비용, 나온 근거." 다음 단계 시작 / 고칠 점 / 여기서 멈춤. |
| 계획 | 단계 끝 카드. 요약의 숫자는 서버가 쓰고, 확신도는 근거 수준을 넘지 못한다. |

- 🔴 🛠 **단계 끝에서 오너가 누른 버튼이 묻혔다.** 다시 전달, 인수 검사 다시, 개발 다시 시도, 회고 다시. 리뷰에서 잡아 고치는 중.
- 🟡 **단계가 끝났다는 걸 콘솔을 안 열면 모른다.** → Slack 알림("검증 단계가 끝났어요, 결정해 주세요")이 사이클 단계 작업에
  기존 결정 알림 종류로 들어간다. 실제로 오는지 확인 필요.

## 9. 개발 (명세 → 빌드 → 머지)

| | |
|---|---|
| 기대 | 무엇을 만들지 알고 승인하고, 만들어진 것을 써 볼 수 있다. |
| 지금 | 명세를 쓰고(자동 시작), 샌드박스에서 빌드, 리뷰, 테스트, 인수 검사. 머지는 결정 카드. |

- 🟡 **만들어진 것을 어디서 써 보나.** 머지 뒤 "사람들이 어디서 쓰나"는 오너가 직접 호스팅하고 주소를 알려 줘야 한다. 이 단계가
  있다는 것을 오너가 미리 모른다.
- 🟡 **빌드 화면의 단계 이름이 개발자 말이다.** Queued, Received, Plan review, Building, Testing, Code review, Shipping, Delivered,
  Merged. 비개발자 창업자에게는 "만드는 중 → 확인하는 중 → 확인 끝, 합칠지 정해 주세요" 정도면 된다.

## 10. 홍보와 반응 확인

| | |
|---|---|
| 기대 | 어디에 무엇을 언제 올릴지 받고, 올린 뒤 반응이 모인다. |
| 지금 | 홍보 묶음 → 내 할 일(게시) → 오너가 올리고 링크 입력 → 반응 수집(정기). 사람 명단과 "사용자가 되기까지" 숫자. |

- 🟡 **링크를 넣지 않으면 반응이 안 모인다.** 이 의존 관계가 할 일 카드에 쓰여 있는지 확인 필요.
- 🟡 **숫자의 출처가 섞인다.** GitHub 별, 오너가 기록한 대화, 회사가 찾은 사람. 무엇이 확인된 숫자인지 화면에서 구분돼야 한다.

## 11. 리뷰 반영과 회고 → 다음 사이클

| | |
|---|---|
| 기대 | 사이클이 끝나면 무엇이 됐고 안 됐는지, 다음엔 무엇을 할지. 타당한 리뷰는 개발로 이어진다. |
| 지금 | 실험 회고(가설, 관측, 원인 후보, 반대 근거, 판정, 다음 제안). 사이클이 들어오면 회고의 다음 제안이 다음 사이클 제안으로 간다. |

- 🟡 **"리뷰 흡수"가 하나의 흐름으로 보이지 않는다.** 사용자 반응 → 타당한 것 고르기 → 개발 → 다시 홍보가 오너가 말한 사이클의
  핵심인데, 지금은 반응 수집, 아이디어함, 개발이 서로 다른 화면에 흩어져 있다. → 다음 사이클 제안이 "지난 사이클에서 받은 반응
  중 이것들을 반영하자"를 명시하게 한다.

## 12. 며칠 뒤 돌아오기

| | |
|---|---|
| 기대 | 콘솔을 열면 "그동안 이런 일이 있었고, 이것이 당신을 기다린다". |
| 지금 | 대시보드 상태 문장, 경고 묶음, 오늘 할 일. Slack 브리핑(설정 시). |

- 🟡 **"그동안"이 없다.** 마지막으로 본 뒤에 무엇이 바뀌었는지(끝난 단계, 새 결정, 쓴 비용)를 모아 주는 곳이 없다. 활동 화면은
  전부를 시간순으로 보여 줄 뿐이다. → 대시보드 맨 위에 "지난번 이후" 한 덩어리.

## 13. 문제가 생겼을 때

- 🔴 **실패 원인이 화면에 안 보였다.** egress 꺼짐 → 로그에만. 사용량 한도 대기, 워커 꺼짐은 경고로 보이지만 샌드박스 상태는 없었다.
- 🔴 ✅ **Ctrl+C가 이상했다.** 고쳤다.
- 🟡 **실패한 업무에 "다시 시도"와 "그냥 두기"가 있지만, 다시 시도해도 같은 이유로 실패할지 오너는 모른다.** 실패 이유가
  환경(오너가 고칠 수 있음)인지 내용(회사가 다시 해 봐야 함)인지 나눠 보여 준다.
