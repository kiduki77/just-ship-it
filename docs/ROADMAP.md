# Roadmap

목표는 두 단계예요. **1.0은 아이디어에서 첫 사용자 100명까지, 3.0은 100명에서 1,000명까지** 오너가 직접 만나는 방식으로 가요. 큰 목표(1.0, 2.0, 3.0) 사이는 작은 단계로 쪼개서 셉니다. 1.0 전에는 `0.2, 0.3 …`, 2.0 전에는 `1.1, 1.2 …`, 3.0 전에는 `2.1, 2.2 …`예요. 숫자는 약속이 아니라 순서 표시예요.

## 규칙

1. **한 아이디어는 한 단계.** 새 아이디어는 나오는 순간 한 단계에 배정하고, 지금 단계가 아니면 [BACKLOG.md](BACKLOG.md)에 단계 태그만 붙여요. 만들지 않아요. 단계를 옮기려면 오너가 정해요.
2. **시간은 고정, 범위는 변동.** 한 단계는 1~2주 상자예요. 안 맞으면 범위를 줄이고 시간을 늘리지 않아요.
3. **상자가 끝나면 된 것만 내보내요.** 연장은 한 번까지, 남은 일이 "내리막"인 필수 항목일 때만이에요.
4. **80%쯤 지나면 얼려요.** 그 뒤는 고치기만 해요. 새 아이디어는 다음 단계로 가요.
5. **끝났다고 볼 조건은 시작 전에 적어요.** 조건에 없는 일은 그 단계가 아니에요.
6. **덜 끝난 조각은 "실험" 표시를 달고 먼저 내요.** 바뀌거나 빠질 수 있다고 화면에 적고, 정식으로 올릴 조건도 함께 적어요.
7. **열린 단계는 하나, 모양을 잡아 둔 다음 단계는 하나.** 나머지는 한 줄짜리 항목으로 둬요.
8. 한 일은 [CHANGELOG.md](../CHANGELOG.md)의 `Unreleased`에 쌓고, 단계가 끝나면 그 버전 아래로 옮겨요.

**영원히 하지 않는 것.** 커뮤니티에 자동 게시, 대량 콜드 메일, 가짜 리뷰와 인위적 참여, LLM API 키.

(4) 배치는 모델 호출이 없는 규칙(인력 파견 매니저)이 하고 이유를 남긴다. (5) 기존 데이터는 지우고 시작한다. 옛 업무나 개발 작업이 있으면 마이그레이션이 멈춘다. (6) `GET /crews`가 업무와 개발 작업의 구성, 이유, 비용, 결과를 준다. 처음에는 모든 업무를 검토하는 설정으로 동작을 그대로 두고 기록만 쌓은 뒤 혼자 하기를 켠다 |

GitHub 유입 숫자(읽음, 최소, 같은 호스트 한 줄)는 시험 사업에 저장소가 없어 시험으로만 확인됐다. 태그 링크와 말할 문구를 본 카드 두 장은 시험용으로 손으로 만든 것이다 ([tracking.md](design/tracking.md)의 실제 실행 기록) |
| 0.6 | 첫 10명 키트 | 완료 (2026-11-16). 실제 시험 사업(B-4)에서 실제 모델 호출로 확인했다. 명단 탭 맨 위에 오늘 연락할 사람 최대 3명이 이유와 함께 보였다. 버튼 한 번에 메시지 초안 2개, 프로필 문구 세 길이, 초대 문구 2개가 쓰였고(약 24초), 글자 수와 제한, 복사 버튼이 붙었다. 공개 글에서 찾아 아직 연락하지 않은 사람은 초안 없이 "먼저 그 사람의 글에 직접 답을 달아 주세요"가 보였다. 이미 연락한 지인에게는 다음 할 일을 따르는 후속 메시지가 쓰였다(처음엔 첫 연락처럼 써서 프롬프트를 고쳤다). 그 사람이 새 말을 남기자 초안에 "반영되기 전에 쓴 글"이 붙었고, 쓰는 중의 두 번째 클릭은 거절됐고, "연락했어요"가 단계를 옮겼다. 키트는 결정 카드를 만들지 않았고 보내는 경로가 없다. 오늘 화면에 키트로 가는 줄 하나가 보였다. 두 언어, 어두운 테마, 1440·1200·900·390에서 봤다. 거절된 문구, 다시 쓰기 실패 뒤 이전 문구가 남는 것, 사용 한도 대기, 장소가 없을 때, 10명이 차서 접히는 것은 시험과 임시 DB에서만 확인됐다. 화면 낭독기의 실제 낭독은 듣지 않았다. 한 번도 연락한 적 없는 지인(찾음 단계)의 초안은 실제 실행에서 보지 않았다 ([first-ten-kit.md](design/first-ten-kit.md)의 실제 실행 기록) |
| 0.7 | 글로벌 채널 정리 | 완료 (2026-11-16). 채널마다 규칙을 그 사이트의 원문에서 읽었는지가 정해졌다. 읽은 곳은 "규칙 확인됨"과 읽은 날짜, 원문 링크가 붙고, 못 읽은 곳은 "규칙 미확인"과 이유가 붙는다. 미확인인 곳에는 주간 홍보가 카드를 만들지 않고, 에이전트가 낸 글 카드도 거절된다. 2026-11-16에 원문을 읽은 글로벌 채널은 Hacker News, Show HN, Product Hunt, dev.to, Hashnode, LinkedIn(새로 추가), Lobsters(새로 추가), GitHub 릴리스 8곳이다. dev.to는 원문이 AI가 도운 글로 자기 사업을 홍보하지 말라고 해서 회사가 요점만 주고 오너가 쓰는 곳으로 바뀌었다. Reddit과 X는 읽기가 막혀 미확인이고, Discord·뉴스레터·Awesome 목록은 곳마다 규칙이 달라 미확인이다. 한국 채널은 다시 조사하지 않아 긱뉴스만 확인됨이다. 실제 시험 사업에서 확인했다. B-4의 주간 홍보는 프롬프트에 dev.to만 넣었고 제목과 본문 없이 요점만 쓴 카드가 나왔으며, 기록에 규칙 때문에 뺀 8곳의 이름이 남았다(그 카드는 시작한 단계가 없어 내 할 일에는 들어가지 않았다). B-5(동네 가게형)는 맞는 채널이 모두 미확인이라 모델 호출 없이 "올릴 글을 만들지 않았어요"와 뺀 채널 이름이 남았다. 숫자 탭의 "채널과 규칙" 목록과 글 카드의 표시를 두 언어, 두 테마, 1440·1200·900·390에서 봤다. 실제로 못 본 것: 에이전트가 낸 글 카드의 거절, 결정 카드의 표시(가짜 응답으로만 봄), 오너 자기 장소 카드. 설계와 남은 빈틈은 `docs/design/channel-rules.md`. |

## 2.0까지: 지역과 직접 접근

| 단계 | 주제 | 끝났다고 볼 조건 |
|---|---|---|
| 1.1 | 지역 묶음 구조 | 시작할 때 "어디에 서비스하실 예정인가요?"를 묻는다(기본 글로벌). 묶음은 채널, 규칙, 법 점검표로 이루어진다 |
| 1.2 | 한국 묶음 | 지금 한국 채널을 묶음으로 옮긴다. 규칙은 실제 플랫폼 화면에서 확인한 것만 "확인됨"으로 표시한다 |
| 1.3 | 직접 연락 | 연락처 저장(출처, 동의 메모, 보관 기간, 삭제, 연락 금지), 지역별 발송 전 점검표, 기존 이메일 커넥터와 사람 목록의 연결 정리 |
| 1.4 | 개발자 제품용 기회 찾기 | 해커뉴스(Algolia)와 GitHub 이슈를 읽기 전용으로 읽는다. Reddit은 검색 링크만 준다. 카드에는 글 링크와 근거만 담고 답글 문장은 쓰지 않는다. 관련 글 비율을 재서 기록한다 |
| 1.5 | Slack 승인 | Slack에서 카드를 승인하고 거절한다. 결정 기록은 콘솔과 같다 |
| 1.6 | Gmail 연결 | 메일 읽기와 승인 후 발송. 기본은 보관함 |
| 1.7 | 두 번째 지역 묶음 | 일본 등 한 곳. 묶음 구조(1.1)가 실제로 맞는지 확인한다 |
| **2.0** | **지역과 직접 접근 완성** | 위 전부 |

## 3.0까지: 100명에서 1,000명으로

첫 100명은 아는 사람과 커뮤니티에서 오지만, 1,000명은 한 번 한 일로는 안 와요. 되풀이되는 채널을 찾아서 키우는 단계예요. 1.0과 2.0이 쌓은 채널별 기록이 여기서 쓰여요.

| 단계 | 주제 | 끝났다고 볼 조건 |
|---|---|---|
| 2.1 | 채널별 성과 비교 | 추적 기록으로 "어디서 온 사람이 남았는지"를 보여 주고, 힘을 실을 채널과 접을 채널을 제안한다 |
| 2.2 | 되풀이되는 채널 | 글과 검색 유입 초안(오너가 고쳐 쓴다), 추천과 대기자 명단 구조, 소개 요청 문구 |
| 2.3 | 남게 하기 | 처음 가치를 얻은 뒤 다시 쓰는지 본다. 안 돌아오는 사람에게 물을 문구를 준비한다 |
| 2.4 | 본인 계정 연동 | "내가 승인한 것만 보내기"로 공식 API를 통해 승인한 글을 예약하고 게시한다 |
| 2.5 | 작은 예산 광고 시험 | 오너가 상한을 정했을 때만 한다 |
| 2.6 | 오픈소스 공개 준비 | 라이선스, 보안 검토, 다른 사용자의 설치와 첫 실행 |
| **3.0** | **100명에서 1,000명** | 위 전부. `PRODUCT.md`의 100명 목표를 1,000명으로 함께 고친다 |

## 근거와 한계

- 규칙과 번호 체계는 다른 오픈소스의 공개 문서를 읽고 정했어요: SemVer(0.y.z는 초기 개발, 1.0.0은 약속 확정), Rust와 Python과 SQLite의 얼림, Shape Up의 시간 고정과 연장 제한, Kubernetes와 Rust의 실험 표시. 읽지 못한 부분(혼자 하는 프로젝트의 이슈 라벨 규칙, 동시 진행 제한)은 근거 없이 제가 추가한 규칙이에요.
- 단계 내용과 순서는 조사와 오너의 결정을 바탕으로 한 제안이고, 1.0 이후 단계는 1.0이 끝나기 전에 다시 쪼개요.
- 연락처 저장과 직접 발송을 1.3으로 미룬 이유: 한국 정보통신망법 제50조는 광고 전송에 사전 동의를 요구하고 B2B 예외가 없어요. 개인정보 의무는 믿을 만한 출처를 못 찾았어요.
- 홍보 조사의 한계: 오너가 직접 쓴 사례와 숫자가 적고, 한국 채널은 사례가 없어요. Reddit의 읽기 접근은 2026년 말부터 닫히는 중이라는 보도가 있어요(원문 미확인).
