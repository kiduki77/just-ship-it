# Language: English and Korean

Just Ship It ships worldwide, so English is the default and Korean is the other choice. The owner picks one in
Settings > Language. It switches the console and everything the company writes for the owner from then on: the CEO's
kickoff replies, decision cards, reports, drafts, idea-panel warnings, to-dos and the status sentences the server
writes.

This page explains the mechanism, where the glossary lives, how to convert a file, the lint that keeps Korean
inside the catalogs, and how the remaining files split into six lanes.

**Every lane writes to two style rules.** The Korean follows [KOREAN-STYLE.md](KOREAN-STYLE.md): 해요체,
conclusion first, active, no 번역체. Read it before you write a Korean string; its worked examples cover the most
visible strings in every lane. The English is natural English written for an English reader, not a translation of
the Korean. Write each language from what the screen means, and never word-for-word from the other one.

## The setting

`app_settings.general.language` is `"en"` or `"ko"`, default `"en"`. The `app_settings` table stores it as a section
row, so it needs no migration. `app_settings.language()` reads it.

There is one setting for the whole company. A single owner reads every business, and a console that switched
language when the owner switched business would be harder to read than one that never does. A per-business override
is not built. If one is ever needed, `Business` gets a nullable `language` column, and the only code that changes is
the one place each boundary reads `app_settings.language()`.

A change takes effect at once:

- **Console.** The Language section saves the setting, then calls `setLanguage()`. The whole console re-renders
  from the root (`main.tsx` keys the app by language). The browser keeps the last language it saw, so a reload paints
  in that language before `/api/settings` answers.
- **New AI output.** Every agent call reads the setting when it starts (see the output-language rule below).
- **Server text.** Every read model reads the setting per request.

Text already written stays in its language: an agent's card, a report, a stored title or summary. The console shows
it as written, with the words around it in the current language. Nothing is machine-translated after the fact. A
Korean title on an English screen is expected after a switch. The `prose()` glossing in `labels.ts` stays Korean
because it rewrites inside Korean text.

## The glossary

`backend/justshipit/i18n/glossary.py` is the single source of the owner's words: one word per idea in each language, what
it means, the code name it maps to, and the retired words testers found confusing. Three things read it:

- **The console.** It reads the table through `web/src/i18n/areas/term.ts` (`term.plan`, `term.plan.means`, and so
  on). That file is generated, so run `uv run python -m justshipit.i18n.glossary` after editing the table.
- **The agents.** Every agent's output-language rule lists the terms in the chosen language, with "never call it"
  for each retired word.
- **People.** PRODUCT.md's terminology table repeats the table.

`tests/test_i18n.py` fails when `term.ts` is stale, when PRODUCT.md lacks a term, or when any catalog uses a retired
word.

Each agent's name is in the glossary too (`ROLES`, read with `glossary.role(agent_id, lang)`), so a server sentence
names a reviewer the way the sidebar does. `tests/test_agent_names.py` fails when the console's `label.agent.<id>`
says something else.

| English | Korean | Replaces |
|---|---|---|
| Plan | 계획 | 지시서, work brief |
| Experiment | 실험 | 도전 |
| Decision | 결정 | 결정함 |
| To-do | 내 할 일 | 오너 할 일 |
| Got value | 도움 됨 | 첫 가치, first value |
| Steps to first users | 사용자가 되기까지 | 사다리, ladder |

The full table is in PRODUCT.md and `glossary.py`. Code names do not change: the `bets` table, the `brief` API field
and `first_value` stay as they are. Only labels the owner reads change.

## Console: `t()` and the catalogs

Catalogs live in `web/src/i18n/areas/<area>.ts`, one file per area. Each entry holds both languages side by side, so
a key cannot be added in one language only:

```ts
export const home = {
  "home.today.more": { en: "{n} more in My to-dos", ko: "내 할 일에서 {n}개 더 보기" },
  "home.status.decisions": { en: { one: "{n} decision is waiting for you.", other: "{n} decisions are waiting for you." },
    ko: "결정할 일이 {n}건 있어요." },
} as const satisfies Area<"home">;
```

- `t(key, vars)` returns a string and `tx(key, vars)` returns a node, for a value that is an element (`<b>3</b>`,
  a `<Link>`). The compiler checks the key and the exact values each message takes, in both languages.
- `{name}` is a value. `{name|을}` adds the Korean particle that fits the value's last sound. Write either form of
  the pair (을/를, 이/가, 은/는, 과/와, 으로/로, 이에요/예요, ...). After a Latin letter both are written: "Slack을(를)".
  Prefer a sentence that puts a fixed word after the value, so no particle depends on it.
- An English message that counts something is `{ one, other }`, chosen by `n`. Korean needs no pair.
- `PlainKey` is the type for a table of keys a screen picks from at render time (`Record<string, PlainKey>`).
- `lookup(key)` is for a key built from a server code (`label.status.${code}`). It returns `undefined` when there is
  none.
- `locale()` is the Intl locale (`en-US`, `ko-KR`) for dates, numbers and relative times. Never write `"ko-KR"`.
- Never call `t()` at module scope. A constant built there keeps the language the page loaded with. Keep keys at
  module scope and call `t()` while rendering.
- `labels.ts` reads the `label` area for statuses, agents, activity verbs, entities, purposes and routines.

`catalog.ts` imports every area once. Each lane owns its area files, so no two lanes edit the same file. Add a key to
your lane's area. If one lane's area grows large, split it into `<area>-<part>.ts` and add the import to `catalog.ts`.

## Server: `msg()` and the catalogs

Catalogs live in `backend/justshipit/i18n/messages/<area>.py`, as `MESSAGES: dict[str, Entry]` with keys
`<area>.<name>`. `justshipit.i18n.catalog()` finds every module in that package, so adding an area touches no other file.
`msg(key, lang, **vars)` formats with the same `{name}`, `{name|을}` and `{one, other}` rules as the console.

- **Read the language once at the boundary.** An API route or a job handler calls `app_settings.language()` and
  passes `lang` down as a keyword argument. Services do not read it themselves. `api/today.py` and
  `services/today.py` are the pattern.
- **Prefer data over sentences in stored server text.** A summary the server writes into a row the console shows
  later (activity, notices) is frozen in the language of the moment. New code stores the facts in `data` and lets the
  console render the sentence, as `eventText()` already does for status changes. Existing summaries stay as they are.
  Slack notices work this way: a `contracts/notify.py` builder stores its fixed words as a `Said` (a catalog key and
  its values), and the sender words them in the language it reads when it sends. Callers pass codes, not words
  (`owner_task(..., kind="post")`, `usage_wait(reason="usage_cap_day", ...)`). A daily-briefing line is a function
  of `(session, lang)`.
- **Error messages the owner sees** (`HTTPException` details, `describe()` refusals) go through `msg` too. Read the
  language in the route that raises. A service refusal is an `i18n.said.Refusal` holding a `Said`
  (`ResponseRejected`, `OwnerTaskError`): the route words it with `exc.words(lang)`, and `str(exc)` is the English a
  log line or the CLI reads. A reason a rule returns to another module (`policy.door_rule_problem`,
  `channels.link_problem`, `owner_quote.problem`) is a `Said` too, worded with `say(reason, lang)` where it is shown.
- **Writes that every job reaches** (`requests.create`, `owner_tasks.done`/`skip`/`reopen`, `door_rules.derive`)
  read `app_settings.language()` once at their own entry, since their callers are every lane's job handlers. What
  they store for the owner (activity summaries, door-rule notes) is worded in that language.
- **An error raised far from the boundary** (a sandbox or runtime check deep under a job) raises
  `i18n.said.SaidError(key, **vars)` or a subclass (`SandboxUnavailable`, `SetupRefused`, `MergeRefused`). The
  boundary renders it with `said.words(exc, lang)`, which also finds a `SaidError` or a `Refusal` on the `__cause__`
  chain. `str(exc)` is the English text, for logs.
- **A job's step log stores keys.** `engineering/worker.py` writes each step's owner line as `{"key", "vars"}`
  (`_say`) and `worker.step_line(step, lang)` renders it when it is shown. A step from before keeps its Korean text.

## Matching words in both languages

Some rules read text an agent or the owner wrote: verdict words, copy rules, ID scrubbing, number checks, channel
aliases. Stored text keeps the language it was written in, so a rule always reads every language at once, never only
the current one.

Put each rule's words in `backend/justshipit/i18n/match/<rule>.py` as one table per language
(`WORDS: dict[Lang, ...]`) and join them in the service. `match/verdicts.py` with `services/verdicts.py` is the
pattern. English fragments are whole words (`_en()` there: a letter or a hyphen beside one makes it part of another
word, so "hold" is not in "stakeholder"), since Korean particles sit against the word and Korean has no edges.
Apostrophes are made plain first (`i18n.match.plain`), so "Don’t" with any apostrophe is "Don't".
`match/owner_text.py` also holds `GLOSSARY`, the owner's words for a field name an agent wrote; it is chosen by the
text the name sits in (any Hangul: Korean), since a validator has no setting to read. Still to move:

- `services/launch_gate.py`, and the kickoff number checks in `services/kickoff.py`.

Channel names, aliases and rules in `config/channels.yaml` are per-language already, and a business's market
(`audience.market_of_business`) picks its places with its customer description: `channels.for_market` and
`people.where`. A
refusal that names a channel carries the name in every language (`Said` takes a `{lang: text}` value), so it is still
worded in the reader's language when the boundary says it.

## AI output

`agents/executor.py` appends `i18n.prompting.output_rule(lang)` to every call's system prompt, whether the caller
used a prompt file or its own override. It names the language, what stays as written (quotes, names, code, file paths,
commit messages, a draft for a community in another language), that JSON keys and enum values stay as the schema
gives them, the style, and the glossary terms. It comes last so it outranks a language a prompt file names. For Korean
the style line is KOREAN-STYLE.md in a few sentences; keep it short, because every call carries it
(`tests/test_korean_style.py` caps it). The product being built is not owner text: its UI, copy, README and code
follow its spec, and an engineering run's rule covers only the fields the owner reads. The spec writer records the
product's language as a tag (`SpecDraftOut.product_language`, from who the users are), the server writes it at the top
of `prd.md` and into `HandoffTarget.language`, the engineer and the reviewer are told to follow it, and the acceptance
check takes its captures with chromium in that language. A spec from before it falls back to the owner's language.

The kickoff follows the setting too, not the language the owner types in. Before this change the CEO answered in the
owner's language. That rule is gone because the kickoff writes the plan, and the plan's lines are system text the
console shows next to labels in the setting's language. A plan whose lines switch language with each answer would be
harder to read than one in the language the owner chose. The owner's own words are still quoted as written, so a
quote and its line can be in different scripts. Then the CEO's `quote_gloss`, the quote in the line's language,
stands in for the quote's words in the check that the quote is about the line (`services/owner_quote.py`). The quote
must still be the owner's verbatim, and a gate line's numbers must still come from the owner's words. A Korean
owner on the English default gets English replies until they switch. So while the owner writes in the other language,
the kickoff's answer box shows one quiet line in the language they write in: they may keep writing so, the CEO replies
in the setting's language, and a link to Settings > Language (`kickoff/LanguageHint.tsx`).

Prompt files stay Korean for now. Each one now defers to the output-language rule, so none of them pins Korean any
more. They should become English, because English is the project's working language and Korean examples in a prompt
pull Korean phrasing into English output. Each lane translates its own prompts and its contracts' `Field(description=)`
text, which the model reads as part of the prompt. Prompts are not linted (they are internal), but the lint does count
Korean in contract descriptions. Until a prompt is English, its Korean must follow KOREAN-STYLE.md, because the model
copies a prompt's phrasing and retired words into what the owner reads. KOREAN-STYLE.md lists the prompts that need it
most.

Length limits stay written in Korean characters (`OneLine(70)`). `contracts.owner_text.clip` stretches a limit by
`EN_LENGTH_FACTOR` (1.8) for a text that is not mostly Hangul, and the output rule tells the agents the same factor.
Give an explicit English limit only where 1.8 is wrong for a field.

## The lint

`tests/test_i18n.py` fails when:

- a TS/TSX file under `web/src` (outside `web/src/i18n`) or a module under `backend/justshipit` (outside `justshipit/i18n`
  and migrations) has a Korean string, or a pinned Korean locale, and is not in `tests/i18n_hangul_allowlist.txt`.
  Comments and docstrings do not count.
- a file on the allowlist has no Korean left, which means its line has to go, or holds more Korean lines than the
  `# N` after it. Lower N as a file shrinks; never raise it.
- a catalog entry lacks a language, the languages take different values, a plural lacks `n`, or a message uses a
  retired word.
- a `msg("...")` key does not exist, or `term.ts` or PRODUCT.md drifts from the glossary.

`uv run python tests/i18n_kit.py` lists what is left, file by file, with line counts.

`tests/test_owner_text_surfaces.py` fails when a catalog message carries a code name, a flag, a brief line id or a
registry path (`contracts.owner_text.leaks`, the same patterns the scrub drops), outside a short list of exceptions
with their reasons. It also feeds the task document, the merge card, what approving does, the spec card's trace and
the alerts code-shaped input in both languages, and holds what they write to the same contract. A server sentence
says a status, a verdict or an agent in the owner's words from a catalog, never as the code it stores.

`tests/test_i18n_particles.py` fails when a ko message writes a particle by hand right after a value
("{when}이에요", "{name}을(를)"), when `{value|을}` follows a value that may end in a Latin letter (an agent's name,
a channel, a title), or when an en message glues a count to its unit ("{current}/{target}{unit}"). A value that
always ends in Hangul or a digit goes in its `ENDS_IN_HANGUL_OR_DIGIT` table with the reason. Money and percent
are not such values: "$5.00" reads 달러 and "80%" reads 퍼센트, so the sentence puts a fixed word after them.

`tests/test_korean_style.py` fails when a ko message in any catalog uses a mechanical 번역체 pattern (합니다체,
되어지, 에 있어서, 하도록 하겠, 성공적으로, 을 통해, 의 경우, 에 의해, 그것, 당신, ...), or when too many lean on
"~에 대해". A justified exception goes in its `ALLOW` table with the reason.

## Converting a file

1. Read the file and list its owner-facing strings. Aria labels, titles, placeholders, error messages and toasts
   count. Code comments do not.
2. Add entries to your lane's area with both languages. Write each from the meaning: natural English, and Korean
   that follows KOREAN-STYLE.md and the glossary. Rewrite the old Korean as you move it; a 합니다체 server sentence
   becomes 해요체 in the catalog, and the style lint fails until it does. The worked examples in KOREAN-STYLE.md
   already cover the most visible strings.
3. Replace each literal with `t()`, `tx()` or `msg()`. Move module-scope string tables to tables of keys.
4. Replace date and number formatting with `locale()`. Replace a hand-written particle (`kickoff/types.ts` has one)
   with `{name|을}`.
5. Delete the file's line from `tests/i18n_hangul_allowlist.txt`.
6. Run `cd web && npx tsc -b` and `bash scripts/test-linux.sh tests/test_i18n.py tests/test_korean_style.py <the file's tests>`. Then look
   at the screen in both languages at 1440 wide.
7. A test that asserted a Korean server sentence passes `lang="ko"` explicitly and keeps its assertion. Add one
   English assertion per converted function.

## Lanes

The remaining files split into six lanes with no file in two lanes. The allowlist lists each lane's files under a
`# lane <name>` heading, with their line counts at the start. Each lane converts its web files, its server modules,
its contracts' descriptions and its prompts, so it can verify a whole screen end to end.

Order and conflicts:

- All six lanes can run in parallel. Each owns its area files and allowlist block. Only `catalog.ts` and the allowlist
  are shared, and a lane touches only its own lines there.
- **build** waits for `fix/product-quality` to land. That branch edits `engineering/worker.py`, `engineering/specs.py`,
  `contracts/handoff.py` and the engineer and spec prompts.
- **decide** and **company** should start after `fix/live-verify-2` lands. It edits `services/requests.py`,
  `services/owner_tasks.py`, `contracts/owner_text.py`, `engineering/status.py` and `api/console.py`. It also edits
  `services/today.py` on the same lines this foundation converted. The conflict is mechanical: keep its
  `owner_text.title(...)` calls and this branch's `msg(...)` reasons.
- The Korean shims the lanes left for each other (`REASON_KO`, `KIND_KO`, `STATUS_KO`, `FIXED_CHECK`,
  `Place.name`, `RETRO_BUDGET_STOP`) went when the lanes were merged, and their callers pass the owner's language.

## Follow-ups

- **Korean defaults still in place.** `roadmap.UNMIGRATED` is the default `lang` of about a dozen roadmap functions;
  every production caller now passes the owner's language, but the tests still lean on the default. Pass `lang` in
  the tests, then drop the default. `BriefSpec.title`/`holds`/`drives`/`default` and `PROVENANCE_KO`
  still give the kickoff and agent prompts Korean words; agents read them, the owner does not.
  `owner_tasks.view` still sends `kind_ko`/`status_ko` (now in the owner's language) beside `kind_label`/`status_label`.
- **One test helper for the owner's language.** `conftest.korean_owner` patches the setting, `lang_kit.owner_speaks`
  saves it, and `test_kickoff.owner_language`, `test_i18n_review.language` and `test_roadmap_language.language` each
  save it their own way. Keep `korean_owner` for "the owner reads Korean" and `owner_speaks` for "the owner switches",
  and move the three local fixtures onto `owner_speaks`.

- **Live install.** On merge the live console turns English, because English is the default. The owner switches to
  Korean in Settings > Language once.
- **Engineer progress log.** The engineer's raw progress log stays in English (`fix/product-quality`, finding A4).
  The owner-facing summary follows the setting.
